# Execution modes and decision points

This is the **only** file where the difference between "there is a human who
answers" and "there is nobody" exists. No skill contains the words "ask the user":
where it meets a fork, it points to a decision point in this file.

Adding a new execution environment in the future means touching this file, not the
skills.

## The detection rule

**Positive marker, and nothing else.**

```
The mode is INTERACTIVE if and only if the request contains the line
  MODE: interactive

In every other case the mode is AUTONOMOUS.
```

No other heuristic. In particular it is **not** inferred from the presence of a tool
for asking questions, and **not** inferred from the platform.

**Why a positive marker and not a negative one.** An earlier version of this rule
said "autonomous if it says `MODE: autonomous`, otherwise check whether there is a
channel to ask questions". That is dangerously wrong: a tool for asking for
clarification can be present even in environments that run with nobody in front of
them, and "the turn was opened by a message" is true also for a message generated by
a webhook. The result is an agent that believes it is in a conversation, asks a
question, and **blocks for ever** waiting for an answer that will never come —
leaving a meeting half-processed.

With the positive marker the error always falls on the safe side: if someone forgets
to write it in an interactive session, the agent does not ask and leaves a record
marked for review, which you fix in thirty seconds. The opposite error costs a lost,
silent piece of work.

**Practical consequence for you:** in Claude Code, if you want the agent to ask you
questions instead of getting by on its own, start the request with
`MODE: interactive`. Or put it once and for all in your project instructions
(for example in your `CLAUDE.md`).

## The non-destructive rule in autonomous mode

In autonomous mode you may **only**:

- create pages;
- append text;
- fill **empty** properties;
- add values to a multi-select.

You may **not**: empty a property, replace the value of an already-filled property
with a different value, delete blocks or pages, rewrite an existing history.

Intended consequence: a wrong analysis run at three in the morning **cannot destroy a
profile built over six months**. At most it produces one more contradiction to work
through. Real corrections are made in an interactive session (DP-4) or by hand on
Notion.

## The decision points

| ID | Situation | Interactive | Autonomous | Trace left |
|---|---|---|---|---|
| **DP-0** | several candidate files among the incoming transcripts | asks which | takes the oldest unprocessed one, one per run | file name in the report |
| **DP-1** | speaker with a generic label carrying substantial content | asks who it is | `Status = Speakers to identify`; writes briefing and dynamics on the Meeting; **touches no profile**; stops | line in `## To confirm` with minute and quote |
| **DP-2** | several People match the search token | asks which | **does not choose**: treats the speaker as DP-1 | list of candidates in `## To confirm` |
| **DP-3** | proper name with no match in People | asks whether to create, with which Category and Relationship | **does not create the person**: treats the speaker as DP-1 | line in `## To confirm`: "person not in the archive, confirmation needed before creating" |
| **DP-4** | the new datum contradicts an already-filled property | shows both versions and asks whether to overwrite | **does not overwrite**: appends to *Contradictions / to verify* | the contradiction itself |
| **DP-5** | there is an unprocessed meeting with the same person (in `prepare-meeting`) | asks whether to process it first | goes on with what it has and says so | warning at the top of the output |
| **DP-6** | the meeting's `Category` or `Type` is ambiguous | asks | `Category` = the majority one among the participants, on a tie `Other`; `Type` = `Meeting` | line in `## To confirm` |
| **DP-7** | the meeting date is uncertain | asks | uses the recording date; if missing, the processing date | line in `## To confirm` |
| **DP-8** | empty, truncated or illegible transcript (quality gate G4) | asks how to proceed | `Status = Error` + `Error message` filled | the error message |
| **DP-9** | deletion of a person | lists the impact and **waits for explicit confirmation** | **refuses** and reports, without deleting anything | no change |

### Note on DP-3

The initial design had the agent, in autonomous mode, create the person with
`Category = Other`. It was changed: **it does not create**. A person created
automatically from a misread label generates a ghost profile that then has to be
found and deleted, and meanwhile receives writes. Stopping costs a confirmation;
getting it wrong costs a clean-up.

## The confirmation gate before writing profiles

Independent of the decision points. If `preferences.confirm_before_writing_profiles`
is `true` **and** the mode is interactive, the agent shows the proposed delta
(current value → proposed value → reason → quote) and waits for an ok before touching
the properties.

The Meeting page is created anyway: the raw material must be made safe in any case.

In autonomous mode this gate does not apply — there is nobody to confirm — but the
non-destructive restrictions above apply instead.

## What it takes to run this system unattended

It does not concern manual use, but it constrains how the skills are written:

- **nothing needs to be done** to get autonomous mode: it is the default, and the
  absence of the `MODE: interactive` marker is enough. That is why the rule is
  written with a positive marker;
- the environment must have the Notion access tools enabled. Environments that
  receive payloads from external sources often start with a restricted tool set for
  security, and in that case processing fails at the deduplication check;
- **the payload must not carry the transcript text.** Environments that receive
  webhooks truncate long fields, and a truncated transcript analysed as if it were
  complete is a silent error. The payload carries identifier, date, title and
  expected length; the skill fetches the text, and compares the length obtained with
  the expected one;
- the report delivery channel is configured outside the skills. No skill relies on
  the chat as its destination: it returns text to the caller and leaves delivery to
  the environment.
